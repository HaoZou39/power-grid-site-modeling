# 温州设计院选址软件前端实施规格

> 状态：SPEC
> 目标：交给另一个 Agent 实现前端，不在本文中直接编写代码
> 适用范围：`frontend/` 及其直接依赖的 API 适配，不改动算法数学实现

## 1. 摘要

前端需要把“选址问题 → 决策者配置 → 算法运行 → 候选解比较 → 结果解释”串成一条清晰的工作流。使用者首先应该知道当前问题使用了哪些数据、约束和目标，然后能够用表单完成一次可复现的运行，最后能在地图、指标卡、Pareto 关系和候选解详情之间切换，而不必阅读 JSON 或服务器日志。

第一阶段优先复用当前已有的实验产物和 API：静态地图 PNG、Pareto HTML、CSV/JSON artifact，以及 `/jobs` 的任务状态接口。等真实算法插件接入后，再逐步增加交互式地图和更细的决策支持功能。前端不实现目标函数、约束或算法逻辑。

## 2. 目标用户和使用场景

主要用户是温州设计院参与选址决策的工程人员和项目负责人。他们关心：

- 当前选址区域和数据是否正确；
- 候选点是否满足不可建设区域约束；
- 地形、道路和需求点目标之间如何权衡；
- 算法是否完成、使用了什么配置；
- 哪些方案可行、方案之间的取舍是什么。

他们不应该被迫理解 Python 模块名、raw pose、normalization 或内部队列。技术细节可以在“运行详情”或“数据详情”中展开，但不应成为主流程的第一层信息。

## 3. 设计原则

1. **先解释问题，再允许运行。** 页面必须先展示区域、数据图层、约束和目标顺序，避免用户在没有上下文时直接提交参数。
2. **一个页面只突出一个主要动作。** 配置页的主要动作是“检查并运行”，结果页的主要动作是“选择和比较方案”。
3. **表单是领域配置的唯一入口。** 不要求用户手写 JSON；组件由插件或配置 schema 生成字段，并显示单位、默认值和校验错误。
4. **结果先看可行性，再看优化取舍。** 不可行解不能与可行 Pareto 解使用相同的视觉权重。
5. **所有数字都带语义。** 例如 `road_distance` 显示为道路距离，单位为 `m`；`n_feasible` 显示为可行方案数，而不是只显示字段名。
6. **前端保持薄。** `api.ts` 负责 HTTP，组件负责展示和交互，后端/算法负责计算。不要在 React 中复制目标函数、Pareto 判断或坐标转换。
7. **先保持浅层目录。** 当前前端文件数量不大，按功能拆成清晰模块即可；只有出现第二个复用者时才新增共享目录或抽象层。

## 4. 当前代码基础和实施边界

当前前端已经具备以下基础：

- `App.tsx`：应用外壳、健康状态，以及“问题与运行 / 实验结果”视图切换；
- `problem_overview.tsx`：问题概览；`problem_snapshot.ts`：实验产物到 `ProblemSnapshot` 的适配；
- `job_workspace.tsx`：插件列表、任务配置和提交；`run_monitor.tsx`：配置页的任务轮询；`run_status.ts`：状态文案；
- `config_form.tsx`：按 JSON Schema 渲染中文分组配置表单；`config_check.ts`：提交前检查；
- `experiment_browser.tsx`：实验目录；`result_explorer.tsx`：方案地图、详情和表格；`solution_record.ts`：方案 CSV 适配；
- `api.ts`：前端请求和 API 类型；
- `generated/api.ts`：由 OpenAPI 生成的类型文件，不手工维护。

实现 Agent 应在这些模块上演进，不要重新建立第二套请求封装、第二套配置表单或第二套实验 artifact 读取逻辑。目录和职责总览见 `markdown/CODE_MAP.md`。

当前稳定可用的接口是：

```text
GET  /api/v1/health
GET  /api/v1/plugins
POST /api/v1/jobs
GET  /api/v1/jobs/{job_id}
GET  /api/v1/jobs/{job_id}/result
GET  /api/v1/experiments
GET  /api/v1/experiments/{experiment_id}
GET  /api/v1/experiments/{experiment_id}/artifacts/{artifact_id}
DELETE /api/v1/experiments/{experiment_id}
```

当前 `demo.algorithm` 用于验证任务链路；真实算法插件接入前，前端可以使用 fixture 或现有 `outputs/` 目录完成界面开发，但不得把 Demo 结果伪装成正式算法结果。

## 5. 目标页面和工作流

### 5.1 页面结构

主界面是可平移缩放的公开卫星世界地图，选址范围、禁行区和带朝向的帕累托建筑足迹叠加在局部网格上。底图地址集中在 `frontend/src/map/basemap.ts`。决策侧栏只保留定位、建筑尺寸和开始优化，不使用复杂路由框架：

```text
应用外壳
└── 决策地图
    ├── 定位选址区与建筑尺寸
    ├── 开始优化（site.nsga2，不填写目标权重）
    └── 帕累托建筑足迹与道路距离、平整度
```

上方「主页」里的构建或更新场景数据写入 `scenes/`。侧栏只显示场景是否已准备，开始优化只读取该场景。

「文件」里的「导入案例」列出 `outputs/` 中已完成的实验目录。导入读取该目录的 `solutions.csv` 和 `pareto_solutions.csv`，在地图上显示可行帕累托足迹，并从 `resolved_config.json` 的 `modeling.rect_w_m`、`modeling.rect_h_m` 恢复建筑尺寸。删除先要求再点一次确认，然后移除该实验目录。不能删除输出根目录之外的路径，也不能删除正在写入的当次优化目录。

侧栏面向决策者，只放这几项：

- 定位选址区；
- 建筑宽度和高度；
- 开始优化，固定调用 `site.nsga2`，用 NSGA-II 直接比较三个目标；
- 任务状态，以及选中方案的道路距离、地形平整度、需求点距离和可行性。

### 5.2 问题概览：基础展示

页面打开后，用户首先看到问题概览卡片：

- 区域名称或实验名称；
- 栅格范围、宽高、分辨率和坐标约定；
- DEM、不可建设区域、道路和需求点四类数据是否已加载；
- 当前数据来源和 seed；
- 建筑矩形尺寸；
- 目标顺序：`dem_soft`、`road_distance`、`demand_distance`；
- hard feasibility 规则：不可建设区域 hard count 必须为 0。

地图区域至少提供一张基础预览，并显示图例：

- DEM：连续色带；
- obstacle mask：半透明红色；
- 道路：深色线；
- 需求点：橙色点。

第一阶段可以直接使用实验目录中的 PNG。数据尚未准备好时，显示“缺少哪一项”和下一步动作，不显示空白地图或伪造随机数据。

### 5.3 配置与运行：决策者输入

配置表单分为四组，组标题使用中文，字段旁显示单位和说明。

#### 数据与实验身份

- 实验名称；
- 数据输出目录或实验标识（如果后端负责目录，则只显示实验名称）；
- 数据版本/来源摘要；
- 随机 seed。

#### 站点和约束

- 建筑矩形宽度 `rect_w_m`，默认 77 m（110 kV 变电站占地宽度）；
- 建筑矩形高度 `rect_h_m`，默认 51.5 m（110 kV 变电站占地高度）；
- 是否只在可建设区域生成需求点；
- hard feasibility 说明和当前阈值；
- 分辨率字段只读展示，避免用户误改已经生成的数据网格。

#### 目标偏好

- 三个目标的权重或偏好配置；
- 明确显示权重总和必须为 1；
- 提供“均衡偏好”快捷入口；
- 提供“偏地形/偏道路/偏需求点”的预设，但预设必须展开为可查看的实际权重；
- 说明所有目标当前按最小化解释。

#### 算法和运行参数

- 算法选择；
- 算法特有参数由 JSON Schema 生成；
- device、迭代次数、起点数量等参数只在对应算法提供 schema 时显示；
- 显示预计产物类型，不在前端硬编码算法内部参数。

表单提交前必须经过“运行前检查”：

- 必填项完整；
- 数值在合法范围内；
- 权重总和正确；
- 数据产物已存在；
- 实验名称不会覆盖现有结果，或用户明确选择覆盖。

检查失败时在字段附近显示原因，并保留用户输入。检查通过后，唯一主要按钮为“开始运行”。

### 5.4 运行状态：用户需要的操作

运行提交后显示：

- 实验名称和 job id；
- 状态：排队中、运行中、已完成、失败；
- 当前阶段；
- 进度条；
- 最近一条消息；
- 配置摘要；
- 失败原因和重新运行入口。

第一阶段不做复杂日志终端，不把 Python traceback 默认暴露给决策者。技术详情可折叠查看。任务轮询只能由运行状态模块负责，其他组件不得各自轮询同一个 job。

如果后端尚未支持取消任务，界面不要显示假的“取消”按钮；可以保留未来扩展位置，但当前只提供“返回配置”和“重新运行”。

### 5.5 结果探索：最终方案可视化

结果页采用“实验列表 + 结果详情”的两栏布局。

左侧实验列表显示：

- 实验名称；
- 算法名称；
- 完成时间（如果 manifest 提供）；
- 解数量、可行数量、Pareto 数量。

右侧详情按以下顺序展示：

1. **结果摘要**：总解数、可行解数、Pareto 解数、是否存在可行解；
2. **主地图**：优先显示 `pareto_footprints_map.png`，可切换到候选点图、全部可行图和 Pareto 点图；
3. **方案选择**：选择一个候选方案后显示 `x`、`y`、`theta`、三个 soft objective、hard metrics 和可行性；
4. **目标权衡**：显示 Pareto 3D HTML，并提供一个简单的二维对比方式；
5. **方案表格**：支持按可行性、Pareto 状态和目标值排序；
6. **原始产物**：JSON、CSV 提供查看或下载链接。

视觉层级必须遵循：

- 可行方案使用主要颜色；
- 不可行方案降低透明度或默认隐藏；
- 选中的方案使用明显高亮；
- 约束违反使用红色，但不能只靠颜色表达，必须有文字或图标说明；
- 地图、表格和指标卡点击一个方案时同步更新。

### 5.6 结果可视化的分阶段范围

第一阶段（必须完成）：

- PNG 地图预览；
- Pareto HTML iframe 或新窗口打开；
- 摘要指标卡；
- 方案表格或 CSV 查看入口；
- 单个方案详情；
- artifact 缺失时的明确空状态。

第二阶段（在真实算法结果稳定后）：

- 浏览器内二维 Pareto 图；
- 图、表、详情之间的联动选择；
- 按可行性和目标范围过滤；
- 两到三个候选方案并排比较；
- 地图图层开关和图例控制；每个图层必须独立初始化、显示或隐藏，不依赖前一个图层的可见状态。

第三阶段（确有需求再做）：

- 交互式 1 m 栅格地图；
- 候选 footprint hover 和点击；
- 结果标注、批注和导出报告；
- 方案收藏和多人协作。

不要在第一阶段引入 GIS SDK、全局状态框架或复杂图表依赖。现有 PNG/HTML artifact 已经足以验证工作流。

## 6. 前端模块设计

保持 `frontend/src/` 浅层目录，每个文件只表达一个用户功能或一个稳定技术职责：

```text
App.tsx                 应用壳、导航、全局健康状态
api.ts                  HTTP 请求和领域类型
config_form.tsx         JSON Schema 配置表单
job_workspace.tsx       插件选择、运行前检查、任务提交和轮询
experiment_browser.tsx  实验列表、图件预览和结果详情
problem_overview.tsx    数据、区域、目标和约束概览
result_explorer.tsx     方案筛选、比较和联动展示
styles.css              页面布局、颜色、状态和响应式样式
generated/api.ts        OpenAPI 生成文件，只重新生成，不手改
```

如果 `job_workspace.tsx` 或 `experiment_browser.tsx` 继续变大，应按用户功能拆出子模块，而不是把所有代码移动到一个泛化的 `utils` 文件。React 采用组合式功能组件即可，不要求为了“面向对象”而使用 class component；状态必须封装在所属功能模块中。

建议的组件接口以领域对象为中心：

```text
ProblemSnapshot
RunConfig
RunStatus
ExperimentRecord
ArtifactRecord
SolutionRecord
```

组件不应直接依赖后端返回的任意字典。API 层负责把 OpenAPI 响应转换为这些稳定的前端类型，字段语义和单位写在类型旁边或对应注释中。

## 7. 数据和 API 适配要求

### 7.1 已有接口的使用规则

- 任务、场景和实验请求统一经过 `api.ts`。Agent 对话经过 `frontend/src/agent/agent_api.ts`，因为那份契约单独维护；
- API 错误转换成用户可读的中文消息；
- 组件不能拼接后端 base URL；
- artifact URL 只来自后端 manifest，不根据文件名自行猜路径；
- PNG 使用 `<img>`，HTML 使用受限 iframe，JSON/CSV 使用链接或文本查看器；
- artifact 不存在时显示可恢复的空状态，不让整个结果页崩溃。

### 7.2 问题概览的接口扩展

当前 API 还没有正式的问题概览接口。实现 Agent 可以先使用 fixture 或从已有 `resolved_config.json`、`data_metadata.json` 和实验 artifact 组装只读概览，但应把读取逻辑放在 `api.ts` 或独立 adapter 中。

后续建议增加：

```text
GET /api/v1/problem/context
```

返回至少包含：

```text
region
grid: { width, height, resolution_m, coordinate_system }
layers: { dem, obstacle, roads, demand_points }
constraints
objective_order
data_source
seed
```

如果该接口尚未落地，前端必须明确标记“来自实验产物”或“演示数据”，不能把 fixture 当作正式数据。

### 7.3 运行配置和结果类型

运行配置至少要能表达：

```text
experiment_name
algorithm_id
seed
rect_w_m
rect_h_m
objective_weights
algorithm_config
```

结果详情至少要能表达：

```text
solution_id / run_id
x, y, theta
dem_soft
road_distance
demand_distance
obstacle_hard_count
is_feasible
is_pareto
```

字段缺失时显示“未提供”，不要在前端推导或猜测指标。

### 7.4 地图操作与算法数据

地图上的点击、拖拽和画范围不各自对应一套算法接口。交互只改一份地图编辑；算法只从这份编辑里读它认识的字段。经纬度停在地图模块，算法看到的都是场景 1 m 局部坐标：原点在选址范围左上角，x 向东，y 向南。

当前代码由 `frontend/src/map/site_edit.ts` 的 `SiteEdit` 承担这份编辑。禁区、可行域、点选同类、进货原点和拖动方案都只改它。下面是发送口径，新功能按此加，不另开传输。

一份地图编辑包含这几类，坐标都是局部米：

```text
scene_name
building        宽度、高度
policies        山体策略、农田策略、农田代价系数
marks[]         { id, kind, x, y }
regions[]       { id, kind, ring }
poses[]         { id, x, y, theta }
```

`marks` 和 `regions` 用 `kind` 区分用途。现在有三种：`origin` 表示进货原点，最多一个；`exclusion` 表示不可建设范围；`feasible` 表示可行域。两种范围都至少三个顶点。点选同类用地得到的圈写成 `exclusion`。禁区和可行域只出现在「编辑」页，不放在地图右侧。

地图操作只改这份编辑，不直接调用建模或搜索：

| 操作 | 改动 |
| --- | --- |
| 进货原点 | 写入或替换 `kind = origin` 的标记 |
| 禁区、点选同类 | 追加一条 `kind = exclusion` 的范围 |
| 可行域 | 追加一条 `kind = feasible` 的范围 |
| 画圈、方框 | 禁区和可行域下面都有这两个二级选项。画圈松手闭合。方框先点一个角，再点对角线另一角，矩形取这两点的外接边，轴与局部坐标对齐 |
| 删除范围 | 侧栏按钮或橡皮擦点中该范围后，按 id 去掉 |
| 拖动方案 | 只改该方案的 `x, y`，朝向和尺寸不动 |
| 点选方案 | 只改变当前查看的方案 id |

离开选址范围的点不写入编辑。

### 7.5 AI 助手

黑色菜单栏最右边的「AI」按钮打开「AI 助手」。窗口可以拖动和缩放，右上角能最小化。一条回复放在一个气泡里，换行留在气泡内，不按换行拆开。助手的气泡在左侧标志旁，用户的在右侧。回答按字出现，不等整段结束。标志用 Lucide 的机器人图标，许可是 ISC。它只提议改动。操作种类、校验和模型配置以 `markdown/AGENT_MODULE.md` 为准。

面板保留本轮对话，并把当前 `SiteEdit` 收成快照发给 `POST /api/v1/agent/chat`。返回提案时列出差异，地图用虚线预览新增或改动的范围、位姿和进货原点。用户点确认后，`applyOps` 才改这份编辑；提案里若有 `run_search`，接着走现有的 `site.nsga2` 提交。拒绝则丢弃提案。提案发出后地图又被改过，则提案过期，不能确认。

窗口顶部分「对话」和「记忆」两页。提案里带记忆改动时，差异下面列出「将记下」「将改写」「将忘掉」；确认时先写记忆，再改地图。「记忆」页按偏好、常用指令、场景备注列出条目，每条可删除，条数超限时提醒整理。记忆的格式和规则以 `markdown/AGENT_MODULE.md` 为准。

编辑向外只走两条已有通道：

1. 开始优化把整份编辑交给 `site.nsga2`。对应现有任务配置里的场景名、建筑尺寸、用地策略、`exclusion_zones`、`feasible_zones`、`origin_x`、`origin_y`。没有可行域时整个选址范围都可搜索。搜索不在这一步重建场景栅格。
2. 查看或拖完一个方案时，只把该方案的 `x, y, theta`、建筑尺寸，以及 `origin` 标记交给 `POST /api/v1/scenes/{id}/site-report`。这一步不重跑 NSGA-II，也不附带禁区列表。

点选同类用地的 `POST /api/v1/scenes/{id}/landuse-patch` 是场景查询，不是算法输入。它只把一个点击变成一圈顶点；前端把这圈写进 `exclusion` 之后，才和手绘禁区走同一条优化通道。

点中方案矩形时，地图右上角弹出特征小窗，展示经纬度和各项目标，不展示局部米坐标。经纬度只通过 `localToLngLat` 得到。方位角是矩形宽边的方向，正北为 `0°`、顺时针；搜索内部的 `theta` 仍是 `[-pi, pi]`，`0` 表示宽边朝东。关掉小窗不取消选中，点选本身也不改折线图。小窗可以把当前方案加入对比，最多五个；折线图上每条线是一个方案，各项越小越好。纵轴按这次全部帕累托方案固定，加入或去掉一条线不改变其他线的形状。折线用优化结果里的目标值，不改用当前点选方案的实时报告。

以后增加选点、画线或另一类范围时，加一种 `kind`，并在优化配置或单点报告里读这一种。不因为新操作再增加一个提交接口。算法不认识的 `kind` 直接报错，不静默忽略。显示开关、地图平移和定位选址区只影响画面，不进入这份编辑。

## 8. 视觉和交互规范

### 8.1 视觉层级

- 背景使用低对比度中性色，内容卡片保持清晰边界；
- 主操作使用单一强调色；
- 状态颜色固定：运行中为蓝色，成功为绿色，失败/违反约束为红色，警告为橙色；
- 页面标题、步骤标题、字段说明和技术详情使用稳定的字号层级；
- 地图图例始终可见或可通过按钮打开；
- 不用大面积装饰图、自动轮播或与任务无关的指标。

### 8.2 易用性

- 所有输入控件有中文 label；
- 必填字段和单位直接显示；
- 错误信息靠近出错字段；
- 键盘可以完成导航和提交；
- 图片有描述性 `alt`；
- iframe 有标题；
- 小屏幕下先保证表单和方案详情可用，再压缩地图和装饰内容；
- 长列表和大图片使用懒加载或明确的加载状态。

### 8.3 术语

用户界面优先使用：

```text
可建设区域、不可建设区域、道路距离、需求点距离、地形平整度、可行方案、Pareto 方案、目标权重
```

`raw pose`、`normalization`、`scalar`、`hard count` 等词只在技术详情或 tooltip 中出现，并附中文解释。

## 9. 分阶段实施计划

### Slice 1：应用壳和问题概览

- 保留现有 React/Vite 入口；

### Slice 2：决策配置和运行前检查

- 将现有 JSON Schema 表单调整为中文分组；
- 增加单位、默认值、权重和 seed 说明；
- 在提交前执行前端可判断的校验；

验收：用户不看 JSON 就能完成一次配置；错误不会丢失已填写内容。

### Slice 3：运行状态

- 把轮询和状态展示集中到一个模块；

验收：任务状态变化不会导致其他页面重复请求或状态错乱。

### Slice 4：结果探索

- 增加摘要卡、主地图、方案详情和方案表格；

- 添加可行性和 Pareto 的视觉区分。

验收：用户可以从一个实验中选出一个具体方案，并说清它的坐标、目标值和约束状态。

### Slice 5：联动和视觉打磨

- 图、表、详情同步选择；
- 增加二维 Pareto 或简单目标对比；
- 补充响应式布局、键盘操作、空状态和错误状态；
- 删除重复的展示逻辑和无用样式。

验收：桌面端主流程完整，小屏幕下核心操作仍可完成，构建和回归检查通过。

## 10. 验收标准

### 功能

- [ ] 能查看问题区域、数据图层、约束、目标顺序和单位。
- [ ] 能通过表单设置实验名称、seed、建筑尺寸、目标权重和算法配置。
- [ ] 权重非法、尺寸非法、数据缺失时会阻止提交并给出中文原因。
- [ ] 能提交任务并查看 queued/running/succeeded/failed 状态。
- [ ] 能浏览实验目录并选择一个实验。
- [ ] 能查看摘要、主地图、Pareto HTML、方案详情和 CSV/JSON 产物。
- [ ] 不存在某种 artifact 时页面仍然可用。

### 结构

- [ ] 所有请求集中在 `api.ts` 或明确的 API adapter。
- [ ] `App.tsx` 不包含算法参数解析、任务轮询细节或结果文件判断。
- [ ] 问题概览、运行状态、结果探索分别由独立模块负责。
- [ ] 组件不复制后端的目标计算、Pareto 计算或坐标转换。
- [ ] 新增插件字段只需要更新插件 schema，不需要修改通用表单组件。
- [ ] 关键非显然逻辑有注释，注释解释原因和领域约定，而不是重复代码。

### 质量

- [ ] `npm run build` 通过。
- [ ] Python 后端测试通过。
- [ ] API fixture 或集成测试覆盖 loading、empty、error、success 四种结果状态。
- [ ] 不引入没有明确用途的 UI 库、地图 SDK 或全局状态库。
- [ ] 页面不把演示数据标记为正式算法结果。
