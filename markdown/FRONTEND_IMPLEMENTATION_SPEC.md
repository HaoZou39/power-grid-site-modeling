# 温州设计院选址软件前端实施规格

> 状态：SPEC
> 目标：交给另一个 Agent 实现前端，不在本文中直接编写代码
> 适用范围：`frontend/` 及其直接依赖的 API 适配，不改动算法数学实现

## 1. 摘要

前端需要把“选址问题 → 决策者配置 → 算法运行 → 候选解比较 → 结果解释”串成一条清晰的工作流。使用者首先应该知道当前问题使用了哪些数据、约束和目标，然后能够用表单完成一次可复现的运行，最后能在地图、指标卡、Pareto 关系和候选解详情之间切换，而不必阅读 JSON 或服务器日志。

第一阶段优先复用当前已有的实验产物和 API：静态地图 PNG、Pareto HTML、CSV/JSON artifact，以及 `/jobs` 的任务状态接口。等真实算法插件接入后，再逐步增加交互式地图和更细的决策支持功能。前端不实现目标函数、约束或算法逻辑。

## 2. 目标用户和使用场景

主要用户是温州设计院参与选址决策的工程人员和项目负责人。他们关心：

- 当前选址区域和数据是否正确；
- 候选点是否满足不可建设区域约束；
- 地形、道路和需求点目标之间如何权衡；
- 算法是否完成、使用了什么配置；
- 哪些方案可行、方案之间的取舍是什么。

他们不应该被迫理解 Python 模块名、raw pose、normalization 或内部队列。技术细节可以在“运行详情”或“数据详情”中展开，但不应成为主流程的第一层信息。

## 3. 设计原则

1. **先解释问题，再允许运行。** 页面必须先展示区域、数据图层、约束和目标顺序，避免用户在没有上下文时直接提交参数。
2. **一个页面只突出一个主要动作。** 配置页的主要动作是“检查并运行”，结果页的主要动作是“选择和比较方案”。
3. **表单是领域配置的唯一入口。** 不要求用户手写 JSON；组件由插件或配置 schema 生成字段，并显示单位、默认值和校验错误。
4. **结果先看可行性，再看优化取舍。** 不可行解不能与可行 Pareto 解使用相同的视觉权重。
5. **所有数字都带语义。** 例如 `road_distance` 显示为道路距离，单位为 `m`；`n_feasible` 显示为可行方案数，而不是只显示字段名。
6. **前端保持薄。** `api.ts` 负责 HTTP，组件负责展示和交互，后端/算法负责计算。不要在 React 中复制目标函数、Pareto 判断或坐标转换。
7. **先保持浅层目录。** 当前前端文件数量不大，按功能拆成清晰模块即可；只有出现第二个复用者时才新增共享目录或抽象层。

## 4. 当前代码基础和实施边界

当前前端已经具备以下基础：

- `App.tsx`：应用外壳、健康状态，以及“问题与运行 / 实验结果”视图切换；
- `problem_overview.tsx`：问题概览；`problem_snapshot.ts`：实验产物到 `ProblemSnapshot` 的适配；
- `job_workspace.tsx`：插件列表、任务配置和提交；`run_monitor.tsx`：配置页的任务轮询；`run_status.ts`：状态文案；
- `config_form.tsx`：按 JSON Schema 渲染中文分组配置表单；`config_check.ts`：提交前检查；
- `experiment_browser.tsx`：实验目录；`result_explorer.tsx`：方案地图、详情和表格；`solution_record.ts`：方案 CSV 适配；
- `api.ts`：前端请求和 API 类型；
- `generated/api.ts`：由 OpenAPI 生成的类型文件，不手工维护。

实现 Agent 应在这些模块上演进，不要重新建立第二套请求封装、第二套配置表单或第二套实验 artifact 读取逻辑。目录和职责总览见 `markdown/CODE_MAP.md`。

当前稳定可用的接口是：

```text
GET  /api/v1/health
GET  /api/v1/plugins
POST /api/v1/jobs
GET  /api/v1/jobs/{job_id}
GET  /api/v1/jobs/{job_id}/result
GET  /api/v1/experiments
GET  /api/v1/experiments/{experiment_id}
GET  /api/v1/experiments/{experiment_id}/artifacts/{artifact_id}
DELETE /api/v1/experiments/{experiment_id}
```

当前 `demo.algorithm` 用于验证任务链路；真实算法插件接入前，前端可以使用 fixture 或现有 `outputs/` 目录完成界面开发，但不得把 Demo 结果伪装成正式算法结果。

## 5. 目标页面和工作流

### 5.1 页面结构

主界面是可平移缩放的公开卫星世界地图，选址范围、禁行区和带朝向的帕累托建筑足迹叠加在局部网格上。底图地址集中在 `frontend/src/map/basemap.ts`。决策侧栏只保留定位、建筑尺寸和开始优化，不使用复杂路由框架：

```text
应用外壳
└── 决策地图
    ├── 定位选址区与建筑尺寸
    ├── 开始优化（site.guided_search，不填写目标权重）
    └── 帕累托建筑足迹与道路距离、平整度
```

上方「主页」里的构建或更新场景数据写入 `scenes/`。侧栏只显示场景是否已准备，开始优化只读取该场景。「软件更新」在与「文件」「视图」「编辑」同级的「设置」页，不放进地图右侧。点开后要输入这台机器 `.env` 里的 `UPDATE_PASSWORD`。确认后快进拉取当前分支，并重新启动本仓库的页面和接口；工作区有未提交修改、不能快进、或已有更新在进行时拒绝，不停止正在运行的进程。页面会断开，内存中的任务清空。新进程没有就绪时退回拉取前的提交再启动。更新会重启开发服务器，Vite 客户端在服务器恢复后会自动重新载入页面，所以提交时把这次的更新号存进 `localStorage`，载入后接着轮询。有结果后弹窗用大字显示「更新完成」「更新失败，已退回原版本」或「更新失败」，下面是脚本消息和当前版本号，同时弹出提示，并清掉存下的更新号。页面已重新载入时按钮是「知道了」；没有重新载入时是「刷新页面」，因为旧页面里的前端代码要刷新才换成新的。提交后 60 秒内状态里一直没有这次的更新号、也没有更新在进行，判为「更新没有开始」，原因看 `outputs/dev-servers/update.log`。助手不能代为更新。

「文件」里的「导入案例」列出 `outputs/` 中已完成的实验目录。导入读取该目录的 `solutions.csv` 和 `pareto_solutions.csv`，在地图上显示可行帕累托足迹，并从 `resolved_config.json` 的 `modeling.rect_w_m`、`modeling.rect_h_m` 恢复建筑尺寸。删除先要求再点一次确认，然后移除该实验目录。不能删除输出根目录之外的路径，也不能删除正在写入的当次优化目录。桌面端导入案例面板默认宽度为 560 px，左侧、顶部和底部分别保留 380 px、148 px 和 18 px，并允许内容纵向滚动；宽度不超过 900 px 时恢复流式宽度。

侧栏面向决策者，只放这几项：

- 定位选址区；
- 建筑宽度和高度；
- 开始优化，固定调用 `site.guided_search`，用引导式多目标搜索直接比较三个目标；
- 任务状态，以及选中方案的道路距离、地形平整度、需求点距离和可行性。

### 5.2 问题概览：基础展示

页面打开后，用户首先看到问题概览卡片：

- 区域名称或实验名称；
- 栅格范围、宽高、分辨率和坐标约定；
- DEM、不可建设区域、道路和需求点四类数据是否已加载；
- 当前数据来源和 seed；
- 建筑矩形尺寸；
- 目标顺序：`dem_soft`、`road_distance`、`demand_distance`；
- hard feasibility 规则：不可建设区域 hard count 必须为 0。

地图区域至少提供一张基础预览，并显示图例：

- DEM：连续色带；
- obstacle mask：半透明红色；
- 道路：深色线；
- 需求点：橙色点。

第一阶段可以直接使用实验目录中的 PNG。数据尚未准备好时，显示“缺少哪一项”和下一步动作，不显示空白地图或伪造随机数据。

### 5.3 配置与运行：决策者输入

配置表单分为四组，组标题使用中文，字段旁显示单位和说明。

#### 数据与实验身份

- 实验名称；
- 数据输出目录或实验标识（如果后端负责目录，则只显示实验名称）；
- 数据版本/来源摘要；
- 随机 seed。

#### 站点和约束

- 建筑矩形宽度 `rect_w_m`，默认 77 m（110 kV 变电站占地宽度）；
- 建筑矩形高度 `rect_h_m`，默认 51.5 m（110 kV 变电站占地高度）；
- 是否只在可建设区域生成需求点；
- hard feasibility 说明和当前阈值；
- 分辨率字段只读展示，避免用户误改已经生成的数据网格。

#### 目标偏好

- 三个目标的权重或偏好配置；
- 明确显示权重总和必须为 1；
- 提供“均衡偏好”快捷入口；
- 提供“偏地形/偏道路/偏需求点”的预设，但预设必须展开为可查看的实际权重；
- 说明所有目标当前按最小化解释。

#### 算法和运行参数

- 算法选择；
- 算法特有参数由 JSON Schema 生成；
- device、迭代次数、起点数量等参数只在对应算法提供 schema 时显示；
- 显示预计产物类型，不在前端硬编码算法内部参数。

表单提交前必须经过“运行前检查”：

- 必填项完整；
- 数值在合法范围内；
- 权重总和正确；
- 数据产物已存在；
- 实验名称不会覆盖现有结果，或用户明确选择覆盖。

检查失败时在字段附近显示原因，并保留用户输入。检查通过后，唯一主要按钮为“开始运行”。

### 5.4 运行状态：用户需要的操作

运行提交后显示：

- 实验名称和 job id；
- 状态：排队中、运行中、已完成、失败；
- 当前阶段；
- 进度条；
- 最近一条消息；
- 配置摘要；
- 失败原因和重新运行入口。

第一阶段不做复杂日志终端，不把 Python traceback 默认暴露给决策者。技术详情可折叠查看。任务轮询只能由运行状态模块负责，其他组件不得各自轮询同一个 job。

如果后端尚未支持取消任务，界面不要显示假的“取消”按钮；可以保留未来扩展位置，但当前只提供“返回配置”和“重新运行”。

### 5.5 结果探索：最终方案可视化

结果页采用“实验列表 + 结果详情”的两栏布局。

左侧实验列表显示：

- 实验名称；
- 算法名称；
- 完成时间（如果 manifest 提供）；
- 解数量、可行数量、Pareto 数量。

右侧详情按以下顺序展示：

1. **结果摘要**：总解数、可行解数、Pareto 解数、是否存在可行解；
2. **主地图**：优先显示 `pareto_footprints_map.png`，可切换到候选点图、全部可行图和 Pareto 点图；
3. **方案选择**：选择一个候选方案后显示 `x`、`y`、`theta`、三个 soft objective、hard metrics 和可行性；
4. **目标权衡**：显示 Pareto 3D HTML，并提供一个简单的二维对比方式；
5. **方案表格**：支持按可行性、Pareto 状态和目标值排序；
6. **原始产物**：JSON、CSV 提供查看或下载链接。

视觉层级必须遵循：

- 可行方案使用主要颜色；
- 不可行方案降低透明度或默认隐藏；
- 选中的方案使用明显高亮；
- 约束违反使用红色，但不能只靠颜色表达，必须有文字或图标说明；
- 地图、表格和指标卡点击一个方案时同步更新。

### 5.6 结果可视化的分阶段范围

第一阶段（必须完成）：

- PNG 地图预览；
- Pareto HTML iframe 或新窗口打开；
- 摘要指标卡；
- 方案表格或 CSV 查看入口；
- 单个方案详情；
- artifact 缺失时的明确空状态。

第二阶段（在真实算法结果稳定后）：

- 浏览器内二维 Pareto 图；
- 图、表、详情之间的联动选择；
- 按可行性和目标范围过滤；
- 两到三个候选方案并排比较；
- 地图图层开关和图例控制；每个图层必须独立初始化、显示或隐藏，不依赖前一个图层的可见状态。

当前决策地图的 GIS Layers V1 从顶部常驻「图层」按钮打开独立浮动面板。面板标题栏支持拖拽，折叠后仍可移动，关闭后重新打开保留本次页面内的最后位置；标题栏按钮不触发拖拽。面板严格包含八项：地形分析的 DEM 高程；土地利用的农田、建筑、道路区域、水体；交通与规划的 OSM 道路网络、禁区、可行域。卫星底图、规划区域边界和优化候选方案固定显示，不加入开关。原「视图」页不再重复提供四类土地利用开关。

DEM 和 OSM 道路默认关闭，四类土地利用沿用原默认状态，禁区与可行域默认开启。DEM 使用场景真实最小/最大高程图例，单位为 m，透明度默认 60%，并明确说明约 10 m 原始 DEM 到 1 m 工作网格的重采样关系。OSM 道路直接显示 `road_segments_local.npy`，经现有 `SiteFrame` 转到地图坐标；它与 landuse 的道路区域是两个独立图层。禁区和可行域共用 `forbidden-zones` source，只通过 `kind` 过滤显示；隐藏不删除 `SiteEdit` 数据，也不改变 `searchConfig()`。启用任一范围绘制工具时，自动恢复该类型可见。图层开关和透明度只更新地图，不提交优化任务。

第三阶段（确有需求再做）：

- 交互式 1 m 栅格地图；
- 候选 footprint hover 和点击；
- 结果标注、批注和导出报告；
- 方案收藏和多人协作。

不要在第一阶段引入 GIS SDK、全局状态框架或复杂图表依赖。现有 PNG/HTML artifact 已经足以验证工作流。

### 5.7 候选站址人工调整

决策地图允许对已经选中的 Pareto 候选方案做一次人工微调，但人工调整不是重新优化，也不能在前端重新实现评价公式。

- 拖拽只改变候选方案中心坐标，建筑宽高和当前朝向保持不变；
- 边界校验必须使用旋转后矩形的四个真实角点。拖拽到规划区域外时，把中心限制到最近的合法位置，保证完整矩形仍在区域内；
- 角度输入对用户使用度，内部 pose 和 API 仍使用弧度。方案小窗通过“方位角（宽边）”的 1° 数字步进控件调整朝向，数值变化后立即生效；旋转后若完整矩形越界，则拒绝该角度并保留上一个合法角度；
- 每个候选方案保留优化结果中的原始 `x`、`y`、`theta`，用户可以一键恢复原始方案；
- 拖拽过程中只更新地图。松手、应用角度或恢复原始方案后，调用 `/api/v1/scenes/{scene_id}/pose-objectives` 重新评价，并明确显示加载、成功和错误状态；开始重新评价时把该方案目标标为「重算中」，禁止把旧指标显示成新位置结果；
- 精确重算请求必须带上当前场景、建筑尺寸、山体/农田策略、农田代价、手绘禁区、可行域和可选进货原点。后端返回前不得用前端估算值或模拟值代替真实评价；`site-report` 只补充施工坡度和进场路径报告；
- 重新评价结果复用现有指标列表，以“原值 → 调整后值”表达变化。规划区域内违反建设约束的方案可以保留，但必须明确标记为不可行；
- 本功能不改变引导式多目标搜索的目标、约束或 Pareto 集，不写入数据库，不修改候选方案对比图表。

当前选中方案的详情卡与候选变电站中心之间使用一条非交互式青绿色引导线建立视觉对应。站址端点由 MapLibre 把候选中心投影到浏览器视口坐标，卡片端点根据详情卡实时 DOM 边界自动选择最近边缘；地图移动、缩放、站址调整以及卡片拖拽、缩放或内容布局变化时同步更新。站址移出地图、详情卡关闭、端点尚未完成测量或站址落在卡片内部时隐藏引导线。该线仅是界面提示，不写入选址数据，也不表示道路、供电线路或其他真实地理连接。

AI 助手、GIS 图层、候选站址详情和方案对比四个浮动窗口共用一份页面内显示顺序。窗口首次显示、关闭后重新打开或切换到另一候选站址详情时自动置顶；按下窗口任意可见区域、通过键盘聚焦窗口内容、开始拖拽或调整大小时也置顶。普通数据刷新、AI 流式回复、GIS 图层状态变化、地图平移缩放和已打开对比面板增减曲线不改变已有层级。层级切换只调整窗口显示顺序，不重置位置、尺寸、折叠状态或内容；SchemeCard 引导线仍处于地图提示层，不覆盖其他浮动窗口。

桌面端 GIS 图层面板首次显示在地图工作区右下方，默认底部余量为 52 px，并与 AI 助手的默认水平中心对齐；常规 310 px 面板宽度下等效为距工作区右侧 155 px。实际位置继续受工作区边界和顶部安全距离限制。用户手动拖动后保留该位置，普通重渲染、AI 助手移动和图层状态变化不触发复位。宽度不超过 900 px 时沿用现有流式布局，不强制套用桌面端偏移。

`/pose-objectives` 接收当前编辑和一个或多个候选 pose；单个方案在接口内形成一行 `[1, 3]` 位姿。它调用 `experiments.launch_site_run.evaluate_form_poses()`，后者复用搜索的约束装配、`evaluate_pose_batch()` 和 `compute_hard_constraints()`，返回方案表同列的软目标、硬指标和可行性；不启动搜索，也不在接口内重写目标或约束公式。

## 6. 前端模块设计

保持 `frontend/src/` 浅层目录，每个文件只表达一个用户功能或一个稳定技术职责：

```text
App.tsx                 应用壳、导航、全局健康状态
api.ts                  HTTP 请求和领域类型
config_form.tsx         JSON Schema 配置表单

如果 `job_workspace.tsx` 或 `experiment_browser.tsx` 继续变大，应按用户功能拆出子模块，而不是把所有代码移动到一个泛化的 `utils` 文件。React 采用组合式功能组件即可，不要求为了“面向对象”而使用 class component；状态必须封装在所属功能模块中。

```

组件不应直接依赖后端返回的任意字典。API 层负责把 OpenAPI 响应转换为这些稳定的前端类型，字段语义和单位写在类型旁边或对应注释中。

## 7. 数据和 API 适配要求

### 7.1 已有接口的使用规则

- 任务、场景和实验请求统一经过 `api.ts`。Agent 对话经过 `frontend/src/agent/agent_api.ts`，因为那份契约单独维护；
- API 错误转换成用户可读的中文消息；
- 组件不能拼接后端 base URL；
- artifact URL 只来自后端 manifest，不根据文件名自行猜路径；
- PNG 使用 `<img>`，HTML 使用受限 iframe，JSON/CSV 使用链接或文本查看器；
- artifact 不存在时显示可恢复的空状态，不让整个结果页崩溃。

### 7.2 问题概览的接口扩展

当前 API 还没有正式的问题概览接口。实现 Agent 可以先使用 fixture 或从已有 `resolved_config.json`、`data_metadata.json` 和实验 artifact 组装只读概览，但应把读取逻辑放在 `api.ts` 或独立 adapter 中。

后续建议增加：

```text
GET /api/v1/problem/context
```

返回至少包含：

```text
region
grid: { width, height, resolution_m, coordinate_system }
layers: { dem, obstacle, roads, demand_points }
constraints
objective_order
data_source
seed
```

如果该接口尚未落地，前端必须明确标记“来自实验产物”或“演示数据”，不能把 fixture 当作正式数据。

### 7.3 运行配置和结果类型

运行配置至少要能表达：

```text
experiment_name
algorithm_id
seed
rect_w_m
rect_h_m
objective_weights
algorithm_config
```

结果详情至少要能表达：

```text

dem_soft
road_distance
demand_distance
obstacle_hard_count
is_feasible
is_pareto
```

字段缺失时显示“未提供”，不要在前端推导或猜测指标。

### 7.4 地图操作与算法数据

地图上的点击、拖拽和画范围不各自对应一套算法接口。交互只改一份地图编辑；算法只从这份编辑里读它认识的字段。经纬度停在地图模块，算法看到的都是场景 1 m 局部坐标：原点在选址范围左上角，x 向东，y 向南。

当前代码由 `frontend/src/map/site_edit.ts` 的 `SiteEdit` 承担这份编辑。禁区、可行域、点选同类、进货原点和拖动方案都只改它。下面是发送口径，新功能按此加，不另开传输。

一份地图编辑包含这几类，坐标都是局部米：

```text
scene_name
building        宽度、高度
policies        山体策略、农田策略、农田代价系数
marks[]         { id, kind, x, y }
regions[]       { id, kind, ring }
poses[]         { id, x, y, theta }
```

`marks` 和 `regions` 用 `kind` 区分用途。现在有三种：`origin` 表示进货原点，最多一个；`exclusion` 表示不可建设范围；`feasible` 表示可行域。两种范围都至少三个顶点。点选同类用地得到的圈写成 `exclusion`。禁区和可行域只出现在「编辑」页，不放在地图右侧。

地图操作只改这份编辑，不直接调用建模或搜索：

| 操作 | 改动 |
| --- | --- |
| 进货原点 | 写入或替换 `kind = origin` 的标记 |
| 禁区、点选同类 | 追加一条 `kind = exclusion` 的范围 |
| 可行域 | 追加一条 `kind = feasible` 的范围 |
| 画圈、方框 | 禁区和可行域下面都有这两个二级选项。画圈松手闭合。方框先点一个角并显示对应颜色的圆形标记，移动时显示半透明填充和虚线边框，再点对角线另一角完成；矩形取这两点的外接边，轴与局部坐标对齐 |
| 删除范围 | 侧栏按钮按 id 去掉；橡皮擦使用专属光标，悬停高亮一个用户范围并提示点击删除，单击后保持橡皮擦模式，Ctrl+Z 可恢复最近一次擦除 |
| 拖动方案 | 只改该方案的 `x, y`，朝向和尺寸不动 |
| 点选方案 | 只改变当前查看的方案 id |

离开选址范围的点不写入编辑。

### 7.5 AI 助手

黑色菜单栏最右边的「AI」按钮打开「AI 助手」。窗口可以拖动和缩放，右上角能最小化。一条回复放在一个气泡里，换行留在气泡内，不按换行拆开。助手的气泡在左侧标志旁，用户的在右侧。回答按字出现，不等整段结束。标志用 Lucide 的机器人图标，许可是 ISC。它只提议改动。操作种类、校验和模型配置以 `markdown/AGENT_MODULE.md` 为准。

面板保留本轮对话，并把当前 `SiteEdit` 收成快照发给 `POST /api/v1/agent/chat`。返回提案时列出差异，地图用虚线预览新增或改动的范围、位姿和进货原点。用户点确认后，`applyOps` 才改这份编辑；提案里若有 `run_search`，接着走现有的 `site.guided_search` 提交；若有 `refine_pose`，走下文「局部优化」。拒绝则丢弃提案。提案发出后地图又被改过，则提案过期，不能确认，按钮变成「关闭」。确认、拒绝或关闭之后，提案框随即收起，结果作为一句助手消息留在对话里（「已确认，地图已更新。」「已拒绝这个提案，地图没有改。」）；发出下一句时，未处理的旧提案框也一并收起。

助手面板有「对话」「记忆」「偏好」三页。「偏好」页给每个目标设 0 到 5 的重要程度，保存到 `PUT /api/v1/agent/preferences/defaults`，并显示已记下几次选择。第一次使用、还没有选择记录时，推荐就按这组设定排序。

方案小窗有「问 AI」按钮：打开助手，把这个方案作为附件放在输入框上方（「方案 3/20 ×」），并预填「分析一下这个方案」。助手窗口可能盖住方案小窗，所以没有附件且有选中方案时，输入框上方另有「＋ 附上方案 N/M」，点一下附上当前选中方案。发送时附件只随这一条消息发出，之后标签清掉，用户气泡上保留方案小标签。附件和分析口径以 `markdown/AGENT_MODULE.md` 为准。

方案小窗还有「记为我的选择」按钮：把当前方案作为选中项、地图上所有带目标值的方案作为候选，发给 `POST /api/v1/agent/preferences/choices`，成功后提示累计次数。带目标值的方案不到两个，或当前方案没有目标值时，只提示原因，不发请求。之后在助手里说「按我以往的选择推荐几个方案」即可用上这些记录。记录格式和推荐口径以 `markdown/AGENT_MODULE.md` 的「偏好推荐」为准。

助手回复带 `recommended` 时，地图按名次给这些方案上色：第 1 到 10 名依次为品红、橙、黄、绿、蓝、紫、粉、棕、青、灰（`RECOMMEND_COLORS`，`frontend/src/map/site_overlay.tsx`）。推荐的方案填充更实、边框更粗，中心放一个同色圆形徽标写名次（DOM marker，底图样式没有字体，图层画不了字），点徽标即选中；其余未选中的方案淡化。选中的方案仍用白色粗边框。推荐只存在页面状态里，刷新页面后需要重新问一次。地图左上角显示「助手推荐」图例，每行「第 N · 方案 K」，点一行即选中该方案；方案小窗标题加「· 推荐第 N」。新的推荐覆盖旧的；点「清除颜色」，或地图上的方案被整体替换（导入案例、重新优化、重建场景、删除当前案例）时清空。局部优化加入的方案不清空已有颜色。

窗口顶部分「对话」和「记忆」两页。提案里带记忆改动时，差异下面列出「将记下」「将改写」「将忘掉」；确认时先写记忆，再改地图。「记忆」页按偏好、常用指令、场景备注列出条目，每条可删除，条数超限时提醒整理。记忆的格式和规则以 `markdown/AGENT_MODULE.md` 为准。

编辑向外走三条通道：

1. 开始优化把整份编辑交给 `site.guided_search`。对应现有任务配置里的场景名、建筑尺寸、用地策略、`exclusion_zones`、`feasible_zones`、`include_demand`、`origin_x`、`origin_y`。`include_demand` 默认关闭：需求点仍是随机点，不参加这次比较。没有可行域时整个选址范围都可搜索。搜索不在这一步重建场景栅格。任务运行期间地图上保留上一轮的方案，新结果读到后才替换；任务失败时旧方案留在原处。
2. 查看或拖完一个方案时，只把该方案的 `x, y, theta`、建筑尺寸，以及 `origin` 标记交给 `POST /api/v1/scenes/{id}/site-report`。这一步不重跑引导式多目标搜索，也不附带禁区列表。
3. 方案被挪动或旋转（拖动结束、角度输入或确认 `update_pose`），恢复原始位置，或助手提案改了建筑尺寸、策略、范围、原点时，把 `searchConfig()`（去掉 `scene_name`）和这些方案的 `x, y, theta` 交给 `POST /api/v1/scenes/{id}/pose-objectives`。接口按搜索同一口径调用现有目标函数和 hard constraint，不重跑引导式多目标搜索。返回的是方案表同样的列，前端写回目标值、禁建覆盖格数和可行性；结果回来前显示「重算中」，成功后显示“原值 → 调整后值”，失败时保留新位姿并明确报错。

点选同类用地的 `POST /api/v1/scenes/{id}/landuse-patch` 是场景查询，不是算法输入。它只把一个点击变成一圈顶点；前端把这圈写进 `exclusion` 之后，才和手绘禁区走同一条优化通道。

点选同类的类型、地图事件、场景查询和写入禁区的实现继续保留，但当前前端不在顶部「编辑」菜单或地图右侧快捷工具栏注册入口。

点中方案矩形时，特征小窗贴在该方框的右下角，平移地图或拖动方框时跟着移动。经纬度只通过 `localToLngLat` 得到；小窗不显示中心位置（m）。方位角是矩形宽边的方向，正北为 `0°`、顺时针；搜索内部的 `theta` 仍是 `[-pi, pi]`，`0` 表示宽边朝东。小窗中的方位角使用 1° 数字步进控件，点击上下箭头即旋转并重新评价；旋转后若完整矩形越界，则恢复上一个合法角度并提示原因。旋转角度仍作为决策信息显示。关掉小窗不取消选中，点选本身也不改折线图。小窗可以把当前方案加入对比，最多五个；折线图上每条线是一个方案，各项越小越好。侧栏需求点距离说明显示「预留接口」；勾选「比较需求点距离」后才显示这一轴。纵轴按这次全部帕累托方案固定，加入或去掉一条线不改变其他线的形状。折线用优化结果里的目标值，不改用当前点选方案的实时报告。

完整优化、历史结果导入和局部优化追加方案成功后，地图继续按 `SiteEdit.withPoses()` 的既有语义选中并高亮默认方案，但不自动打开方案特征小窗。只有用户点击候选矩形或推荐标记、点击推荐图例，或使用 `[ ]` 快捷键切换方案时才打开；关闭后保持当前方案选中，再次点击同一方案可以重新打开。小窗关闭时动态引导线同步隐藏，重新打开后恢复；普通地图平移、缩放、目标值更新和重绘不改变打开状态。

以后增加选点、画线或另一类范围时，加一种 `kind`，并在优化配置或单点报告里读这一种。不因为新操作再增加一个提交接口。算法不认识的 `kind` 直接报错，不静默忽略。显示开关、地图平移和定位选址区只影响画面，不进入这份编辑。

方案特征小窗和方案对比面板只允许通过标题栏拖动，并在桌面端通过右下角手柄调整大小。特征小窗默认 360 × 540 px，切换候选方案时重新贴近该方案；用户手动拖动后，普通地图平移和缩放不覆盖其位置。方案对比面板默认 680 × 400 px，内容区可滚轮滚动，折线图保持居中。两个面板都限制在地图工作区可见范围内；窄屏沿用静态响应式布局。关闭特征小窗后，再次点击同一候选方案必须重新打开。
#### 局部优化

助手提案里的 `refine_pose` 确认后，前端提交一次 `site.guided_search`，配置同第 1 条，只把 `feasible_zones` 换成方案中心周围边长 `2 × half_width_m`、裁到选址范围内的方框。读到这次的可行帕累托方案后不替换地图，按下面的规则挑出几个追加到地图末尾，原方案保留：

- 比较的目标与第 1 条的搜索相同：地形平整度、进场、进场高差；有原点时加沿路长度，打开需求点时加需求点距离。
- 对每个目标 k，在这一项比原方案小的局部方案里，取「其余目标上最大的变差」最小的一个；变差按该目标在局部方案和原方案上的跨度归一。同分时取 k 更小的。重复的只留一个，所以最多加目标个数那么多个。
- 某一项都不比原方案好时，这一项不出方案；一个都挑不出时只提示附近没有更好的点。
- 原方案还在「重算中」时无法比较，每个目标直接取局部最好的。

追加的方案 id 写成 `<实验目录>/<方案表 id>`，并带 `derivedFrom`（快照里是 `derived_from`）指向原方案。小窗标题写「方案 N/M · 由方案 K 局部优化」。完成后选中第一个新方案但不自动打开小窗，并提示是否有各项都不差于原方案的点。规则写在 `frontend/src/map/decision_run.ts` 的 `refinedChoices`。

## 8. 视觉和交互规范

### 8.1 视觉层级

- 背景使用低对比度中性色，内容卡片保持清晰边界；
- 主操作使用单一强调色；
- 状态颜色固定：运行中为蓝色，成功为绿色，失败/违反约束为红色，警告为橙色；
- 页面标题、步骤标题、字段说明和技术详情使用稳定的字号层级；
- 地图图例始终可见或可通过按钮打开；
- 不用大面积装饰图、自动轮播或与任务无关的指标。

### 8.2 易用性

- 所有输入控件有中文 label；
- 必填字段和单位直接显示；
- 错误信息靠近出错字段；
- 键盘可以完成导航和提交；
- 图片有描述性 `alt`；
- iframe 有标题；
- 小屏幕下先保证表单和方案详情可用，再压缩地图和装饰内容；
- 长列表和大图片使用懒加载或明确的加载状态。

### 8.3 术语

用户界面优先使用：

```text
可建设区域、不可建设区域、道路距离、需求点距离、地形平整度、可行方案、Pareto 方案、目标权重
```

`raw pose`、`normalization`、`scalar`、`hard count` 等词只在技术详情或 tooltip 中出现，并附中文解释。

### Slice 5：联动和视觉打磨

- 图、表、详情同步选择；

验收：桌面端主流程完整，小屏幕下核心操作仍可完成，构建和回归检查通过。

### 结构

- [ ] 所有请求集中在 `api.ts` 或明确的 API adapter。
- [ ] `App.tsx` 不包含算法参数解析、任务轮询细节或结果文件判断。
- [ ] 问题概览、运行状态、结果探索分别由独立模块负责。
- [ ] 组件不复制后端的目标计算、Pareto 计算或坐标转换。
- [ ] 新增插件字段只需要更新插件 schema，不需要修改通用表单组件。
- [ ] 关键非显然逻辑有注释，注释解释原因和领域约定，而不是重复代码。

### 质量

- [ ] `npm run build` 通过。
- [ ] Python 后端测试通过。
- [ ] API fixture 或集成测试覆盖 loading、empty、error、success 四种结果状态。
- [ ] 不引入没有明确用途的 UI 库、地图 SDK 或全局状态库。
- [ ] 页面不把演示数据标记为正式算法结果。

## 11. 给实现 Agent 的执行合同

实现前先阅读：

1. `AGENTS.md`；
2. `markdown/CODE_MAP.md`；
3. `markdown/V0_ARCHITECTURE.md`；
4. 本文；
5. `frontend/src/api.ts`、`frontend/src/App.tsx`、`frontend/src/job_workspace.tsx`、`frontend/src/experiment_browser.tsx`。

执行规则：

- 每次只完成一个 Slice，并在完成后运行前端构建；
- 不为了视觉效果引入新的状态管理或地图依赖；
- 不修改算法和建模模块来配合前端假数据；
- API 不足时先建立明确的 fixture/adapter，并记录需要的后端接口，不在组件中硬编码猜测；
- 所有新增字段必须写清单位、来源和空值行为；
- 修改完成后同步 `markdown/CODE_MAP.md`、`markdown/V0_ARCHITECTURE.md` 或本文件中受影响的部分；
- 最终输出改动文件、运行命令、验收结果和仍待后端支持的接口。
