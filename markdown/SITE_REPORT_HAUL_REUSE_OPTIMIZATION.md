# site-report 复用 pose-objectives 的 HaulField

记录日期：2026-10-27。场景：`scenes/lat28.246100_lon120.810600_r4.500km_z18_g9000x9000_rb500m`。

同一 API 进程里，`pose-objectives` 已经建好一份距离场之后，`site-report` 不再为同一身份重新读取和校验约 2 GB 的磁盘缓存。对不上的请求仍走原来的磁盘路径。

## 现有结构

1. 两个接口可以在同一个 Python 进程里执行。当前 API 是单个 uvicorn 进程，没有 `--workers`。两个路由都用 `asyncio.to_thread`，所以是同一进程里的不同线程，堆内存可见。后台 Worker 是另一个进程，不共享这份内存。本次只做同进程复用。

2. 复用前各自持有的对象：
   - `pose-objectives` 的 `_scored_scene`（`lru_cache(maxsize=4)`）保存 `(problem, field)`。键是整份约束 JSON 加 device，里面包含退距、场景名和场景文件签名。
   - `site-report` 的 `_cached_site_report_field`（`maxsize=1`）保存一次 `HaulFieldCacheResult`。键是场景目录、文件签名、原始约束 JSON、原点、高程权重和版本字符串。未命中时调用 `get_or_build_haul_field`，磁盘命中会把约 2 GB 再读入并校验。
   - 磁盘缓存另有自己的 SHA-256 键。那个键包含数组内容，不能拿来做命中检查，因为计算它就要扫描整幅栅格。

3. `pose-objectives` 返回后，`_scored_scene` 仍引用那份 `HaulField`。`evaluate_form_poses` 在场景锁内完成签名和 `_scored_scene`，锁释放后对象还在。`site-report` 随后可以再拿到它。

4. 距离场是否相同，不看场景名，也不只看禁区 JSON。内存复用的身份是：复用版本、解析后的场景目录、`scene_source_signature`（DEM、道路段、道路类别、土地或障碍、`data_metadata`、永农文件的大小和 mtime）、`canonical_haul_constraints`（用地来源、山地策略、农田策略、农田代价、禁区、可行域）、原点、进站高程权重、八连通、`access_road_width_m()`。两边都走 `compose_constraint_masks`、`stamp_constraint_masks` 和 `access_inputs`。道路退距和水体退距只影响建筑足迹，不进入这份身份，这与磁盘键一致。

5. 两个接口的表单并不相同，但通行场用到的部分对齐。`pose-objectives` 的键还带场景名、退距和设备；`site-report` 的 LRU 用的是原始 JSON。这些差异留在各自的旧缓存里。新的复用身份只比较上一条列出的场输入。`field_policy` 未带齐时，`site-report` 仍读障碍文件，不复用按土地合成的场。显式 `obstacle_mask` 也不复用。

6. 必须退回磁盘路径的情况：没有已发布对象；场景文件签名、通行约束、原点、高程权重、连通方式或进站道路宽度任一不同；请求没有用地表单；显式掩膜；对象不是由 `_shared_haul_field` 成功构建或加载后登记的；登记已被更新的一份替换；另一个进程。漏命中可以接受，错命中不可以。

## 实现

`_shared_haul_field` 在 `get_or_build_haul_field` 成功返回后，登记那一个已经校验过的对象。`site-report` 在自己的容量 1 缓存锁之外先查这张表。命中则直接返回同一对象，不复制，也不计算数组哈希。未命中继续原来的 LRU，LRU 未命中再读磁盘。

登记最多保留 1 个引用。查询只拿这把短锁，不在 Dijkstra、整图 EDT 或磁盘读取期间持有。场景锁仍按场景分开，另一幅场景的全图计算不会挡住这次命中查询。

`clear_site_report_cache` 同时丢掉这个引用。场景失效本来就会调用它。

磁盘键、写入格式、1 GB 容量、Dijkstra、`pose_records`、约束规则和四类基础 EDT 缓存都没有改。

## 正确性

`tests/test_construction_report.py` 24 项通过。其中原有 LRU 测试仍是第一次未命中、第二次命中。新增覆盖：

- 同一身份返回同一个对象，运输距离、累计高差、坡度、路线坐标和进站口一致，且不调用磁盘读取、不哈希栅格。
- 禁区、原点、高程权重、农田代价、土地文件 mtime 变化后不复用。挡住站址的禁区使报告变为不可达，而旧场上同一点仍有路线。
- 清空登记后走磁盘读取，路线与原先那份场一致。
- 只保留最近一份引用。
- 显式掩膜不复用已发布的场。

## 楠溪江测量

隔离进程，CPU。没有停 API，没有删除用户缓存。复用计时里禁止了磁盘写入和清理。空禁区这一份场原先不在磁盘上，所以先在内存里建场（Dijkstra 35.87 s）。磁盘回退另起一个进程：临时写入这一份，读完后只删除临时键 `14bc9e6b2327`。用户原有的 `ffdb7859d75281ff3257de85a400682c7244c803bb2a01e4089fa16505707cef` 仍在。

抽样点 `(4499.5, 200.5)`。内存复用与直接 `query_route` 一致：越野 2691.455649052466 m，累计高差 190.46318817138672 m，坡度 16.523225182556043°，进站口 1074，路线 2219 点。

| 测试 | 修改前 | 修改后 |
|---|---:|---:|
| pose-objectives 后首次 site-report | 约 17 s；同场磁盘回退 15.05 s | 0.071 s |
| site-report 热缓存 | 毫秒级 | 0.065 s |
| 内存对象复用命中 | 无 | `memory_reuse`，读场 0 s |
| 不兼容约束回退 | 原路径 | 未复用，重建 36.17 s |
| 峰值 RSS | 只读磁盘的进程 6.77 GiB | 复用不再增加第二份场 |

首次复用日志：`field_cache=memory_reuse field_s=0.000 build_s=0.000`，整次 0.071 s。其中足迹坡度 0.062 s，路线 0.008 s。第二次仍是 `memory_reuse`，整次 0.063 s，读场仍是 0。没有登记对象的新进程第一次是 `disk_hit`，整次 15.05 s，其中 `get_or_build` 8.12 s、建场 0 s；第二次是原 LRU 的 `memory_hit`，整次 0.065 s，读场 0。热缓存没有变慢。

约 17 s 来自先前 API 日志里另一次约束下的 `site-report`（整次 17.216 s，读场 13.540 s）。这次配对比较用的是同一空禁区场：磁盘回退 15.05 s，复用 0.071 s，少约 15.0 s。两次磁盘读的秒数本身会随页缓存波动，不拿 17.216 和 0.071 做比值。

角上 `(10,10)–(40,40)` 的禁区没有命中旧场。报告状态是 `built`，耗时 36.17 s。传给磁盘路径的可行格数是 63,106,978，与按新禁区独立合成的掩膜相同。这个禁区远离抽样路线，所以该点的距离和坐标没变。站址被禁区盖住时路线会变，这由上面的小场景测试覆盖。

复用命中后 RSS 仍是 5.56 GiB，与场发布后相同。不兼容重建后 RSS 升到 8.06 GiB，因为新旧两份场同时在内存里。含建场的进程峰值 9.41 GiB，里面有 Dijkstra 的临时量，以及后来那份重建的场。只走磁盘的新进程峰值 6.77 GiB，校验结束后 RSS 3.13 GiB。命中路径没有为检查身份而复制 9000×9000 数组。

## 不能复用的情况

另一个进程、API 重启、登记为空或已被下一份场替换、场景文件变化、禁区或可行域变化、土地或永农文件变化、道路文件变化、原点变化、进站高程权重变化、进站道路宽度变化、显式障碍掩膜，以及没有用地约束表单的旧请求。这些都会回到原来的磁盘读取或现建路径。
